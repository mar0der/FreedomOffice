# FreedomOffice — server, organisations, permissions and storage

Status: design for the `orgs` branch (2026-11-07). Parts marked **(exists)** are already in the code; §3a
describes what the server implements (Phase 1).

## 1. Storage model (like Microsoft 365)

- **The server is the one source of truth** for shared documents. Every save is a new version; live
  co-editing writes versions on leave and after 15 s idle (at most one a minute). **(exists)**
- **Clients keep an offline cache** of server documents they opened, under their local data folder
  (Linux `~/.local/share/freedomoffice/Server/<host>/`, Windows `%LOCALAPPDATA%\FreedomOffice\Server\<host>\`,
  macOS `~/Library/Application Support/FreedomOffice/Server/<host>/`). Saving while offline keeps the
  local copy and sends it when the connection is back; a conflict with a newer server version is never
  overwritten silently (the user chooses: Save a Copy / Overwrite). **(exists)**
- Personal files: each person has a private root folder ("My files"). Organisation files live in the
  organisation's root folder. Files never belong to a client.

### Server data directory

`data_dir` in `server.toml` (default `/var/lib/freedomoffice`; on the21th
`~/.local/share/freedomoffice-server`):

| Path | What |
|---|---|
| `freedomoffice.db` (+ `-wal`, `-shm`) | SQLite: users, orgs, folders/files metadata, permissions, links, live session state |
| `files/<item-id>/<version>` | the bytes of every kept document version (never changed once written) |

Versions kept: the newest `versions_to_keep` (default 25) plus the first version of each day, plus every named version.

### Backup and restore

- `freedomoffice-server --config <cfg> backup <dir>`: consistent online SQLite copy plus every version file
  (incremental; unchanged files are skipped). Safe while the server runs. **(exists)**
- Production layout: `freedomoffice-backup.timer` nightly to `/var/backups/freedomoffice`.
  On the21th (user service): `freedomoffice-backup.timer` (user unit, 02:30) to `~/.local/share/freedomoffice-server-backup/nightly`.
- **Off-site: dspeter (NAS, 32-bit)** only *receives* copies. It pulls with rsync over SSH from a
  restricted read-only account (`rrsync -ro`), see `server/deploy/nas/`. No `--delete`, so old versions
  survive on the NAS even after the server prunes them. No server binary runs on the NAS.
- Restore: stop the server, copy `freedomoffice.db` and `files/` from a backup into an empty `data_dir`,
  start the server.

## 2. People and organisations

- **Super-admin** (`users.is_admin`, Petar): creates organisations, manages any account. Being super-admin
  does **not** grant access to other people's documents (privacy); it manages accounts and orgs only.
  **Accepted policy:** the super-admin can reset anyone's password and is shown the new temporary password
  once, so they could sign in as that person (as a Microsoft 365 admin can). Every reset is logged as a
  warning (who reset whom, never the password) and signs the person out of every device.
- **Organisation**: name, root folder, members. Member roles:
  - `owner` / `admin`: add and remove people, change roles, see storage use, full control over everything
    in the org folder. (Password resets: super-admin only for now.) They add directly only people who
    already share an organisation with them; anyone else gets an invite. An organisation keeps at least
    one owner.
  - `member`: gets the org's default role on the org folder (`edit` by default, settable to `view`).
- A person can belong to several organisations (family + a team).
- Adding people:
  - **Create account** with a temporary password: generated by the server (random, 16+ chars), shown
    once to the admin, never logged. The person must change it at first sign-in.
  - **Invite by email**: the server makes a one-time invite link (7 days); the admin sends it (the admin
    page opens a prefilled email; there is no mail server). The link offers two choices (as in Microsoft 365): "Create an
    account" (pick a username and password) or "I already have an account" (sign in with it); either
    joins the org with the invite's role. This is also how an org owner/admin brings back someone they
    no longer share an org with (e.g. after removing them).
- Removing a person from an org removes their access to the org folder immediately (including live
  sessions). Their own files stay theirs; files they created in the org folder stay in the org.
- Disabling an account signs it out everywhere **(exists)** and ends its live sessions (new).

## 3. Permissions

Roles on a file or folder: **owner**, **can edit**, **can view** (read-only). Folder roles apply to
everything inside. The effective role is the highest of:

1. owner of the item (or of a parent folder);
2. org owner/admin for items in the org folder → owner;
3. org membership → the org's default role on the org folder;
4. a grant to the person on the item or a parent folder; **(exists, per person)**
5. a grant to a whole organisation the person belongs to (new: `permissions.grantee_kind = 'org'`);
6. a share link (view/edit, optional password and expiry). **(exists)**

**Live changes** (new): when a grant, membership, org role or account state changes, the server
re-checks every open live session on the affected items at once:
- role lowered to view → the server sends `Role{view}`, refuses further edits; the client switches to
  read-only and offers to save the person's unsent changes as their own copy;
- access removed → the session ends with "Your access to this file was removed"; same offer.

## 3a. Server implementation (Phase 1, `orgs-server` branch)

### How organisation ownership is stored

Every organisation has **its own account**: a `users` row with `org_id` set, username `org:<org id>`
(`:` isn't allowed in real usernames, so it can never be signed into or found by name), password hash
`!`, `disabled = 1`. That account owns the org's root folder and, because new items belong to the owner
of their folder, everything created inside it. So:

- the existing owner checks keep working unchanged ("owner of the item" is never a person for org files);
- items can't be moved between an org folder and personal files (different owners) — copy instead;
- restoring from the trash falls back to the org folder;
- removing a person never takes files away from the org;
- the org account is hidden from `/api/users`, the CLI user list and grants; in item JSON the owner of org
  files is `{"username": "", "display_name": "<org name>", "org": "<org id>"}` and the item has
  `"org": {"id", "name"}`.

`Store::role` (three queries whatever the depth: the parent chain is one recursive query, then the org
of the chain's root with the caller's membership, then one query over user and org grants on the chain):
owner → org owner/admin (owner) → org member (`member_role`, edit or view) → max of grants to the person
and to their orgs → share link. `users.is_admin` is not consulted (no implicit document access; note that
the super-admin can still add themselves to an org — that is a policy matter, and it is logged).

### Schema and migration

`PRAGMA user_version` (0 = the schema before organisations, 1 = organisations, 2 = now). `Store::open` runs the migration in
one `BEGIN IMMEDIATE` transaction (a second process opening the database waits and then finds it done; a
crash leaves the old schema). Version 1:

- `users` + `must_change_password`, `org_id`;
- new `orgs(id, name UNIQUE NOCASE, root_id, account_id, member_role 'edit'|'view', created, created_by)`,
  `org_members(org_id, user_id, role 'owner'|'admin'|'member', added_by, created, PK(org_id, user_id))`,
  `invites(id, token_hash, email, org_id, role, expires, created, created_by, used, used_by)`;
- `permissions` rebuilt as `(item_id, grantee_kind 'user'|'org', grantee_id, role, granted_by, created,
  PK(item_id, grantee_kind, grantee_id))`; existing rows are copied as user grants.

Version 2 (web admin, §4): `users` + `last_login`; new `admin_sessions(id, user_id, hash UNIQUE, agent,
created, expires, last_used)`.

Version 3 (Drive, §6): `admin_sessions` + `kind 'admin'|'web'` (existing rows become `admin`); new
append-only `audit(id, at, actor_id, actor_name, ip, action, org_id, item_id, target_user, detail)` with
triggers that abort every `UPDATE` and every `DELETE` of a row younger than 365 days.

Version 4 (Drive review): `audit` + `count`, `last_at`, `last_detail`, `agg_key` (repeats within a minute
are one row); the update trigger now allows only `count` going up (with `last_at` and `last_detail`),
nothing else. The migration drops the version 3 update trigger first (it would refuse filling `last_at`
on a database that has events). the21th (version 2) goes 2 → 3 → 4 in one transaction.

**No downgrade:** an older server binary can't open a migrated database (version 0 code: its schema
statements refer to `permissions.user_id`; version 1 code refuses a newer `user_version`). Back up (`freedomoffice-server backup`) before upgrading.

Deleting an organisation requires its folder to be empty (trashed items don't count); members, grants
to it and invites are deleted, the org account and any trashed items stay (unreachable).

Errors keep the `{"error": "..."}` shape; some add `"code"`: `password_change_required` (403, every
endpoint except `/api/me`, `/api/me/password`, `/api/logout` while a temporary password is set),
`wrong_password`, `links_disabled`, `invite_required`.

Temporary passwords: 20 random characters (about 99 bits), returned once in the response, never logged.
Invites: 32-byte random token (only SHA-256 stored), single use, 7 days; a failed attempt (weak password,
taken username) doesn't use it up; invalid tokens count towards the per-address limit. Accepting is one
transaction and only works while whoever made the invite may still add people with its role (an owner
invite needs an owner; the super-admin always may).
Accepting with an existing account checks the sign-in exactly like `/api/login` (`api::verify_sign_in`,
shared with `check_sign_in`: invalid usernames refused first, the attempt counted up front for the address
and the username, the delay, Argon2 in its semaphore), so wrong passwords there count towards the same
limits. The invite's email doesn't have to match the account (it's only shown). A disabled account (403
"This account is disabled…") or one with a temporary password (403 `password_change_required`) can't
accept; both are said only after the password was right, and they don't use the invite up. Someone
already in the org gets 200 `already_member` and **the invite stays unused** (nothing changed, and it may
have been meant for someone else). The account keeps its own email; `invites.used_by` is set to it. The
membership and the invite's use are one transaction (`Store::accept_invite_existing`), single use; the
live sessions are re-checked afterwards.

Names (`util::clean_name`: files, folders, organisations; created, renamed or uploaded): trimmed, 1-255
characters, none of `/ \ : * ? " < > |` or control characters, not `.`/`..`, and no invisible or
text-direction characters: U+200B-U+200F, U+202A-U+202E, U+2060-U+2064, U+2066-U+2069, U+061C, U+FEFF
(400 "A name can't contain invisible or text-direction characters ..."), except a zero-width joiner
(U+200D) between two emoji, which emoji sequences need. Names stored before this rule stay valid: they
are listed, served, moved and can be renamed to a clean name.

`Strict-Transport-Security: max-age=31536000` on every answer when the server serves TLS itself or
`public_url` is https (not on a plain-http loopback setup).

Passwords (`util::check_new_password`, all new and changed passwords including the CLI): at least 12
characters, not the username and not containing it (usernames of 3+ characters), not one repeated
character, not in the embedded list `server/src/common_passwords.txt` — also after stripping leading and
trailing digits and symbols ("Password2024!" is refused).

Sign-in: after 3 failures for a username within 15 minutes, every attempt for it (right or wrong) first
waits 1 s, 2 s, 4 s, then 8 s (async sleep); the 10-failure lockout per address and username stays. Each
attempt counts as a failure in the same step as the limit check (taken back when it succeeds), so
parallel attempts can't get past the limit. Text that can't be a username is refused before the limiter,
the database and Argon2. The per-address key is the address itself for IPv4 and its /64 for IPv6 (one
host or household usually has a whole /64). Failures are logged as `failed sign-in for user '<name>' from
<ip>` only when such an account exists (`... with an unknown username from <ip>` otherwise, since people
sometimes type their password into the username field; `... with an invalid username ...` for text that
can't be one; never the password). The limiter keeps at most 100 000 keys.

Argon2 (about 19 MiB and one core per run) runs at most once per core at a time, never under the store
lock; requests waiting for it hold no thread.

`allow_links = false` in server.toml: creating a link answers 403 (`links_disabled`), opening one 404, and
link access tokens no longer authenticate.

CLI: `org add NAME`, `org list`, `org members ORG`, `org add-member ORG USER [member|admin|owner]`,
`org remove-member ORG USER` (passwords are still only read from the terminal or stdin).

### Live permission changes (protocol)

After every API change that can affect access (grant/revoke to a person or org, membership add/remove/role,
org `member_role`, org delete, account disable, password reset, sign-out, share link removed, item moved or
trashed) the server re-checks every open live connection before answering; it also re-checks every 30 s for
changes made by the CLI in another process. Re-checks run one at a time, and a connection checks its access
and registers without a re-check in between, so the guarantee is: **once the HTTP response of the change
has arrived, every live connection affected has been told** (and a connection that lost access never gets
it back from an older check). Live tickets are re-checked when used. Per connection:

- role now view (was edit) → `{"t":"role","role":"view"}`; changes it sends afterwards close the connection
  with `4403` (`close::READ_ONLY`) and are not committed;
- role now edit (was view) → `{"t":"role","role":"edit"}`;
- no access any more (grant removed, left the org, account disabled, signed out, link removed, file in the
  trash or deleted) → `{"t":"revoked","reason":"<for people>"}`, then close `4401` (`close::REVOKED`).

Not yet: other participants aren't told that someone's role changed (their peer list keeps the old
`editor` flag until that person reconnects).

### Live co-editing: operations and merge rules (protocol 2)

`GET /api/items/{id}/live` (WebSocket, JSON text frames; crate `cosync` defines both ends). The server keeps
one numbered log of committed batches per document; a client sends one batch at a time against the last
sequence number it has seen (`base`) and the server transforms it over everything committed since
(client/server operational transformation). **Last committed wins** wherever two changes write the same target.

Messages: `hello {sheets, proto}` → `welcome {seq, you, peers, proto}` (+ replay of committed batches) →
`ops {base, id, made?, ops}` / `ack {id, seq, extra}` / `ops {seq, cid, id, by, base?, ops}` (relay) /
`presence` / `snapshot` / `reload` / `role` / `revoked` / `error`.

**Targets** (each is last-writer-wins on its own):

| Operation | Writes target |
|---|---|
| `content {s,r,c,v,adj}` | the cell's **content**: value or formula, with its rich text (`v` null = cleared). The format stays. |
| `format {s,r,c,st}` | the cell's **format**: the whole style (`st` null = default style). The content stays. |
| `cell {s,r,c,v,adj}` | **both** targets of the cell (what protocol 1 sent for every change; still what a command that changes both, such as paste or clear, sends). |
| `note`, `link`, `row_h`, `col_w`, `row_hidden`, `col_hidden`, `row_level`, `col_level`, `merge`, `prop`, `feature`, `book`, `place` | one target each (per cell, row, column, range, key) |
| `rows`, `cols`, `add_sheet`, `del_sheet`, `rename` | structure; moves other operations (below) |

Merge rules:

- A value or formula change and a format change of the same cell, made at the same time, **both survive** on
  every client. Two concurrent value changes: the later commit wins (the earlier one is replaced). Two
  concurrent format changes: the later commit's whole style wins (styles are opaque JSON; there is no
  per-attribute merge, so bold by one person and a fill by another concurrently leaves only the later one;
  the loser is told, see below).
- A `cell` operation that loses against a `content` or `format` operation on the same cell is cut down to
  the part that was not taken (a `format` or a `content`); losing to both drops it. A `cell` that wins
  replaces both parts. So an older client's `cell` operations always work and converge.
- `rows`/`cols` insert or delete moves `cell`, `content`, `format` (and notes, links, sizes, merges) exactly
  alike; content inside deleted rows/columns is dropped; `del_sheet` drops everything on the sheet. A
  `content` or `cell` with a formula records the structure changes it was transformed over in `adj`; the
  receiver adjusts the formula by them as if it had been there (`cell` and `content` alike; `format` has
  no references).
- Undo is per person and is blocked only when someone else wrote the same target since (a value edit is
  not blocked by somebody's formatting).

**Protocol version.** `hello.proto` and `welcome.proto` (absent = 1). Protocol 1 had no `content`/`format`.
A v1 client would apply them as whole cells and diverge, and the server cannot translate them (it keeps no
workbook state, only the log), so the server answers a `hello` with `proto < 2` with
`error "This version of FreedomOffice Sheets is too old to edit this workbook live. Please update the app."`
and closes with `4426` (`close::UPGRADE`); nothing the client sent is committed. A v2 client that gets a
`welcome` without `proto` (an older server) switches to protocol 1 mode: it sends only whole `cell`
operations (every `content`/`format` its diff makes is collapsed into one `cell` carrying the cell's full
current data, also for changes still waiting from before the `welcome`), omits `made`, and shows no
"replaced" messages (an old server relays no `base`). It converges with other clients like any v1 client. Stored logs and live-state blobs from before still replay: `cell` is unchanged.

**"Your change was replaced".** A relayed `ops` carries `base`: what the sender had seen when it *made* the
changes (a batch sent after catching up from offline or while an earlier one was in flight is based on
the newest seq but made against an older one; the client sends that as `made`, the server relays
`min(made, base)`; absent for batches replayed from storage). A client remembers the cell writes of its
recently acknowledged batches (last 32 batches / 20 000 writes, moved along with row/column inserts and
deletes). When a relayed batch has `base` below the seq of one of them and writes the same part of the
same cell with different data, that edit of ours was replaced: the client reports it (cell, what we had
entered, who) unless it has written the cell again since. Edits made after seeing ours, and
value-vs-format, never report. The app shows a non-modal bar "Your change to B3 was replaced by Alice's."
with Show, Restore mine (writes our value again as a new change) and a close button; `fsheets` logs it to
stderr, MCP `write_range` and `replaced_changes` return it under `replaced`.

**Offline, restarts and the journal (M3).** A client that loses the connection keeps editing: changes
are buffered, the status bar says "Offline — changes will be sent when you're back online (N waiting)"
with the countdown to the next attempt (2, 4, then 8 s, jittered), and nothing blocks editing. On
reconnecting it sends `since=<last seq applied>`; the server replays what it has, the client transforms
its pending changes over it and resends. When the server no longer has that base it answers `reload`
(first an `ack` if the client's last batch did commit): the client downloads the latest version and puts
every pending change on top of it as one new batch (tests: 40 changes on one side, 40 plus row/column
inserts and deletes on the other, two snapshots in between). Unsent changes also survive the program
ending, offline or in the middle of sending (`cosync::journal`, used by the app and `fsheets`):

- *File.* One JSON file per (server, account, document) under the data folder
  (`<local data>/freedomoffice/LiveJournal/`, `~/.local/share/freedomsheets-agents/journal/` for
  `fsheets`, or `$FSHEETS_JOURNAL_DIR`), mode 0600 in a 0700 folder, written atomically (temp file,
  fsync, rename) with every local change and whenever a remote batch or acknowledgement moves the
  pending changes (a journal of more than 2000 operations is written at most once a second on such
  events), removed as soon as nothing is pending. It holds the client id, the sequence number the pending
  changes are based on, the batch in flight (id, base, made, operations), the buffered operations, the
  number of changes they stand for, and where the document came from. No password and no token (those
  stay in the sign-in stores).
- *Resuming.* On the next start the app looks for journals, and opens the document of the first one by
  itself (when the window is still the empty one; the others when their document is opened) by asking
  the server for the item (a 404/403 means gone or no longer shared; a network problem retries every
  15 s and keeps the journal). Opening downloads the latest version at seq S as for any join and joins
  with the journal's client id. The journal's changes were made at seq B: the window is read-only for
  the moment it takes the replay to reach B, then the changes are put back (applied to the workbook,
  state for the server's view kept for the usual repair at quiescence) and handled as after a lost
  connection. A batch that did commit before the crash (ack lost) comes back in the replay with the same
  (cid, batch id) and is recognised, not applied twice; the rest is sent. When the file is already newer
  than B (someone's snapshot passed it) the changes are re-based on it like after a long offline period;
  a batch in doubt may then be applied twice if it was committed before that snapshot (known limit).
  Done, the status says "3 changes made offline were saved to the server".
- *Access lost.* If the item is gone or not shared any more at the start, the changes are applied to the
  local copy kept from the last open/snapshot (with its live state next to it) and saved as a copy in
  `LiveJournal/kept/`, which opens with a message; if the account may only view now (at the start, or
  while running), the workbook stays in the window with the changes, read-only, with "Save a copy" and the
  same kept copy; the journal is retired only after that copy was written. If a copy can't be written the
  journal stays. A sign-in that expired keeps the journal and the changes are sent after signing in again
  and reopening.
- *Not covered:* the cell being typed in and the frame's last command are in the journal only from the next
  frame; two app instances on one document and account share a journal file.

### Presence, save state and history in the app (M4)

- **Colour from the user:** a person's colour is a hash of the user name over 12 colours, the same on every
  screen and session (the server's per-session slot is only used for people with a link). Agents
  (`Peer.agent`) are slate grey, drawn with a dashed cursor border, a rounded-square "AI" avatar and
  "(bot)" after the name.
- **People strip** (next to Share): one avatar per person (several windows of one user count once), yourself
  last, an orange dot while they type, dimmed after 60 s without moving. Click an avatar to **follow**: the
  view (sheet and cell) goes where they go until you move yourself, click the avatar again, or they leave.
  Joiners fade in (0.3 s), leavers fade out (0.4 s), and a dropped connection or a reload clears everyone
  at once (no stale cursors). Presence is still per sheet and relayed, never stored.
- **Save state** (title bar and status bar): "Saving..." while a change is unacknowledged, "Saved to server",
  "Offline" / "Offline (N waiting)" (N = changes in the journal not yet sent), "Read-only", "Not connected".
- **Version history dialog:** time, name (click to edit; Enter saves), who changed (contributors, else
  modified-by), size; Restore also works in a live session (the unsaved-changes guard doesn't apply there).
- **Per-user undo** under concurrency is covered by the app tests and by the soak's `undo` action
  (`--undo-pct`, default 8): a client puts its latest text back only while the cell still holds exactly that
  text (found wherever others' row/column changes moved it), else the undo is blocked.

### Comments: threaded comments like Excel 365 (M5, protocol 3)

A *thread* is anchored to a cell: an id, a resolved flag, and comments (the first one, then replies). A
*comment* has an id, the author's user name (`by`; "" for someone with a link) and display name (`name`),
the time it was written (`at`, milliseconds since 1970 UTC, from the writer's clock) and its text (at most
32 767 characters; mentions are written `@Name`), and `edited` (time of the last edit, absent = never).
A thread has at most 1000 comments and a cell can have several threads. Plain notes (`note`) are separate
and unchanged. Ids are GUIDs like `{8F3A9B7C-1D2E-4F50-A1B2-C3D4E5F60718}` (the form Excel uses, so they are
the same in the file).

Operations (protocol 3; every one has the sheet id `s`):

| Operation | Effect | Who |
|---|---|---|
| `thread_add {s,r,c,th}` | adds the thread `th` (`id`, `done`, `comments`) at cell (r, c); ignored if the id exists | anyone who can edit; every comment's `by` must be the sender |
| `comment_add {s,th,cm}` | a reply `cm` to thread `th` | `cm.by` = the sender |
| `comment_edit {s,th,id,text,at,by}` | sets a comment's text and `edited` | only its author (`by` = author = sender) |
| `comment_del {s,th,id,by,adm}` | deletes a comment; the first comment takes the thread | its author, or `adm` |
| `thread_del {s,th,by,adm}` | deletes the thread with its replies | the first comment's author, or `adm` |
| `thread_done {s,th,done}` | resolve (`true`) or reopen | anyone who can edit |

`adm` is true only for a *manager* of the document: its owner, or an owner/admin of its organisation (the
server sets `Peer.manager` from the role it computes anyway). The server checks every comment operation
against the connection before committing: `by` must be the sender's user name, `adm` needs a manager, a
protocol 2 connection and a viewer can't send them (viewers are closed with 4403 as for any change). An
operation that fails the check is dropped from the batch, the rest commits, and the sender gets
`error "You can't change that comment."` and `reload`. Applying repeats the author rule on every client
(`cosync::apply_thread_op`), so all end identically.

Merge rules: operations address threads and comments by id, so they need no transformation over row/column
changes; a `thread_add` in flight moves with rows/columns inserted or deleted above/left of it like a note
and is dropped if its cell's row/column is deleted; threads move with their cell (`shift_threads`) and go
with a deleted row, column or sheet, taking replies, edits and resolves made concurrently with them.
Concurrent `comment_edit`s of one comment and concurrent `thread_done`s are last-writer-wins; adds, deletes
and replies commute. Threads are ordered by (time of the first comment, id), replies by (time, id), never
by arrival. Anything addressed to a thread or comment that is gone does nothing.

**Compatibility.** `PROTO` is 3, `MIN_PROTO` 2. A protocol 2 client (the M4 app / `fsheets`) still connects
and edits cells, but is never sent comment operations (the server removes them from the batches it sends,
also in the replay when it joins; the connection says `proto=<n>` in its WebSocket URL, absent = 2), is
not asked for snapshots, and its snapshot uploads are refused with 426 unless they carry `X-Live-Proto: 3`
(so a client that doesn't know comments can't write a workbook without them over the file). A protocol 3
client that gets a `welcome` with `proto` below 3 turns comments off ("This server can't share comments
yet") and keeps editing as before; with `proto` 1 it speaks protocol 1 as described above.

**In the file.** Written like Excel 365 does: `xl/threadedComments/threadedComment<N>.xml` for sheet N
(`<threadedComment ref="B2" dT="2026-11-07T14:05:09.123" personId="{…}" id="{…}" done="1">` with
`parentId="{first comment id}"` on replies, `<text>`), `xl/persons/person.xml` (`displayName`, `userId` =
user name, `providerId="None"`), the content types and relationships, and a legacy comment on each
commented cell whose author is `tc={thread id}` with the stand-in text Excel writes plus the thread, so
LibreOffice and older Excel show the conversation as a note. Reading: threaded comments become threads,
the stand-in comment is dropped; a file with only legacy comments (e.g. after LibreOffice saved it)
keeps them as notes. `xl/freedomoffice/comments.json` holds what the standard cannot (second threads on a
cell, plain notes on a cell that has a thread, last-edit times), is ignored by other programs and only adds
to what the standard parts say. The lossless live state stored with snapshots has the threads as
`thread_add` operations.

**In the app.** A purple marker in the top-right corner of a commented cell (pale when resolved; notes keep
their red one); hovering shows the thread as a card; clicking the marker, "New/Open Comment" in the cell's
right-click menu, Review > New Comment or Ctrl+Alt+M open the Comments pane on the right: all threads of the
sheet in cell order (filter All / Unresolved / Mine), new comment, reply (Ctrl+Enter), resolve/reopen,
"..." > Edit / Delete (shown only where allowed), `@` completion from the members of the document's
organisation, the people in the session and earlier authors, mentions highlighted. Author names and times
are shown in the viewer's own time zone ("Today 14:05", "Nov 3, 14:05"). Changes appear for everyone at once;
viewers read but don't write (the pane says so); there is no commenter role. In a file that isn't on a server
the author is the person at this computer. Agents' names end in "(agent)".

**For agents.** `fsheets comments list|add|reply|resolve` and the MCP tools `list_comments`, `add_comment`,
`reply_comment`, `resolve_comment` (README in `agents/`).

**For the web viewer** (read-only, same access as the other viewer endpoints):
`GET /api/items/{id}/sheet` has `threads` for all sheets, `GET /api/items/{id}/sheet/comments?sheet=N` the
threads of sheet N (`{sheet, threads, rev}`; 400 for a bad index). Each thread:

```json
{ "sheet": 0, "id": "{8F3A…}", "r": 4, "c": 28, "ref": "AC5", "done": false,
  "comments": [ { "id": "{8F3A…}", "by": "alice", "name": "Alice Admin", "at": 1700000000000,
                  "text": "Is this right? @Bob Builder" },
                { "id": "{91C0…}", "by": "bob", "name": "Bob Builder", "at": 1700000060000,
                  "text": "Yes", "edited": 1700000090000 } ] }
```

`r`, `c` are zero-based, `sheet` is the index in `sheets`, `at`/`edited` are milliseconds since 1970 UTC
(render in the viewer's time zone), `edited` is absent when never edited, the first comment is the thread's,
the rest are replies in order, and `@Name` in the text is a mention (match it against the names you know to
highlight it). Threads are in the JSON of `/sheet` as of the last live change, like the cells (they follow
`rev`). Editing comments from the browser needs bridge operations and is not built.

### Known limits

- Anyone can lock a username out for 15 minutes with 10 wrong passwords (per-username lockout DoS).
- Every sign-out, grant or membership change re-checks all live connections (fine at this scale).
- Live tickets (60 s, single use) aren't limited in number per user.
- Clients older than this server don't know the `role`/`revoked` messages and close codes; they treat
  the close as a lost connection and keep trying to reconnect (each attempt answers 401/404).
- Share-link (`/l/`) and invite (`/i/`) tokens are in URL paths: the server redacts them in its log, but a
  reverse proxy logs them unless told not to (the deploy notes must say so for nginx/Caddy).
- No storage quotas yet (usage is reported only).
- Web admin (§4): the sign-in form has no CSRF token (there is no session yet), only the origin check;
  a POST with neither Origin nor Referer is judged by its CSRF token alone. Sessions aren't bound to an
  address or browser. Destructive buttons (disable, reset, remove) have no "are you sure" step except
  deleting an organisation. The People page runs a few queries per person (organisations, storage):
  fine for a family or a team, slow with thousands of accounts.
- Drive (§6): the audit log records file and folder names, also of personal files, which the super-admin
  can read there (not the contents). Repeated events are counted per minute (§6), so one actor adds at
  most about one row a minute per item or account; failed sign-ins from very many different networks
  still add a row per network and minute (rows go after 365 days, or with `audit-prune`). Browsers that send
  neither `Sec-Fetch-Site` nor `Origin` (very old ones) rely on SameSite=Strict and the CSRF header alone.
  Web sessions, like admin sessions, aren't bound to an address or browser.
- Drive app (§6): the upload conflict pre-check compares names with JavaScript's `toLowerCase()`, the
  server with Rust's `to_lowercase()`; for the rare characters where they differ the server's answer (409,
  then the same question) decides. Cancelling an upload after its last byte was sent can't undo it: the
  server may already have stored it (it then shows up in the folder, and in its version history if it
  replaced a file).

### Web admin (`/admin`, `server/src/admin.rs`)

Plain server-rendered HTML forms served by freedomoffice-server; no JavaScript, no external scripts, fonts
or CDNs; one stylesheet `/admin/style.css` (light, plus `prefers-color-scheme: dark`; usable on phones).
Super-admin and org owners/admins (for their orgs); anyone else who signs in sees "You don't administer
anything" and their own change-password form.

| Route | What | Who |
|---|---|---|
| `GET/POST /admin/login`, `POST /admin/logout` | sign in / out | anyone |
| `GET/POST /admin/password` | change own password (forced first while a temporary one is set) | signed in |
| `GET /admin` | overview: organisations, people, storage (an org admin: of their orgs) | signed in |
| `GET /admin/orgs`, `POST /admin/orgs` | list; create | managers; super-admin |
| `GET /admin/orgs/{id}` | members, add/create/invite, open invites, storage, settings | org owner/admin, super-admin |
| `POST /admin/orgs/{id}/settings` (`member_role`), `/rename`, `/delete` (empty folder, confirm box) | | owner/admin; super-admin; super-admin |
| `POST /admin/orgs/{id}/members` (`username, role`), `.../members/{user}/role`, `.../members/{user}/remove` | | org owner/admin |
| `POST /admin/orgs/{id}/accounts` → temporary password shown once | | org owner/admin |
| `POST /admin/orgs/{id}/invites` → link shown once with a prefilled `mailto:`; `.../invites/{iid}/revoke` | | org owner/admin |
| `GET /admin/people`, `POST /admin/people` (account without org) | status, orgs, last sign-in, storage | super-admin |
| `GET /admin/people/{user}`; `POST .../disable`, `/enable`, `/reset-password`, `/sign-out`, `/admin` (`on=1/0`) | | super-admin |
| `POST /admin/people/{user}/sessions/{device\|web}/{id}/revoke` | end one sign-in (`web`: an admin-page or a Drive browser session) | super-admin |
| `GET /admin/audit?user=&org=&action=&before=` | audit log (§6), 50 per page | super-admin: all; org owners/admins: their orgs |

Every action calls the same functions as the API (`api::create_account_as`, `set_member_as`,
`remove_member_as`, `patch_org_as`, `create_invite_as`, `set_disabled_as`, `reset_password_as`, ...), which
hold the authorization rules (`org_for`, `need_manage`, `need_owner_for`, `need_admin`, `invite_required`,
last owner, last super-admin), and re-checks the live sessions (`App::changed`) before answering. Errors
are shown as a page with the API's message and status (403, 404, 409, ...). After a change the browser is
sent on (303) to the page with a fixed message code (`?m=saved`; no text from the URL is shown).

**Session.** Sign-in goes through `api::check_sign_in`, the same code as `/api/login`: names that can't be
usernames are refused before anything, then the attempt is counted up front in the shared limiter (per
address and username), the delay after repeated failures, Argon2 in its semaphore. Success creates an
`admin_sessions` row (only the SHA-256 of a 32-byte random secret is stored) and sets
`__Host-fo_admin=<secret>; Path=/; Max-Age=43200; HttpOnly; SameSite=Strict; Secure`. It expires 12 h after
sign-in whatever the activity, isn't a bearer token for the API (device tokens aren't admin sessions
either), is checked on every request (disabled account, demoted admin, temporary password), and ends with
sign-out, "sign out of all devices", disable, password reset, and any password change (from the API: all
web sessions end; from the page: all others). Signing in again from a browser ends the session of the
cookie it sent; a person keeps at most 10 sessions (the oldest end). A temporary password allows only
`/admin/password` and sign-out. Nobody resets their own password (web and API, 400 "Use Change password
for your own account."): the reset would sign them out before they saw the new one. Plain-http setups (only possible on loopback or with `allow_insecure_http`, and with an
`http://` public URL) get `fo_admin` without `Secure`, since browsers wouldn't send a Secure cookie back;
anything with TLS or an `https://` `public_url` always gets the `__Host-`/`Secure` cookie. Set `public_url`
behind a reverse proxy: the origin check compares against it.

**CSRF.** Every POST form has a hidden `csrf` field = base64url(SHA-256("freedomoffice admin csrf\0" +
session secret)): one per session, nothing stored, unknowable without the HttpOnly cookie; compared in
constant time (403 when missing or wrong). Before that, a POST whose `Origin` isn't `public_url`'s origin
(`null` included), or that has no Origin and a `Referer` from elsewhere, is refused (403); the sign-in form
has this check (no session yet) and SameSite=Strict. With neither header the token decides.

**Headers** on every response under `/admin` (a router-wide middleware, so also on 400 from a bad path
parameter, 404, 405 and 413): `Content-Security-Policy: default-src 'none'; style-src 'self';
img-src 'self' data:; form-action 'self'; frame-ancestors 'none'; base-uri 'none'`,
`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Cache-Control: no-store`,
`Referrer-Policy: same-origin` (not `no-referrer`: with that, browsers send `Origin: null` on form POSTs,
which would leave the origin check nothing to compare; no referrer leaves the site either way).

**Shown once.** Temporary passwords (create account, reset) and invite links appear only in the response
to the POST that made them (no-store), selectable with one click (`user-select: all`); they are never
logged or stored in clear. Resets are logged as warnings (who reset whom). All user text (names, emails,
device and browser names, org names) is HTML-escaped; an unknown username in a URL is answered with a
fixed "No such user." (API too), never echoed.

## 5. Security baseline (required for any public test)

- Passwords: argon2id; at least 12 characters, not in a common-password list, not the username.
- Sign-in limits: 10 failures per 15 min per IP and per username → locked (HTTP 429) **(exists)**;
  plus exponential delay per username, and failures logged (without the password).
- Bind to `127.0.0.1` behind a reverse proxy; trust `X-Forwarded-For` only from loopback. **(exists)**
- Config option `allow_links = false` to switch off share links on a public trial.
- No secrets in logs, argv or the repo. Temporary passwords and invite links are shown once.

## 6. FreedomOffice Drive (Petar, 2026-11-07: "our own secure OneDrive replacement")

One server, one set of accounts/orgs/permissions for Sheets and Drive. Drive lives in this repo as its own
crate `drive/`: the web app (static HTML/CSS/JS, no external scripts/CDNs, embedded into
freedomoffice-server and served at `/drive`) and, later, the desktop sync client (`drive` binary).
freedomoffice-server stays the only thing that touches the data.

### Where the data lives
- **the21th is the NAS**: `data_dir` on its own disks (WD Reds when they arrive; moving = stop server,
  `rsync -aHAX` data_dir, change `data_dir`, start, verify, keep the old copy until a backup has run).
  Tailscale/LAN only, long term. No public exposure except the temporary the18th trial.
- **dspeter is the off-site copy** (NAS, 32-bit, receives only): it *pulls* the nightly
  `freedomoffice-server backup` output over SSH with a read-only rrsync account, without `--delete`
  (Guardian sets it up; units in `server/deploy/nas/`). The server can't delete or overwrite backups.

### Ransomware / mistake recovery (security first)
- Every save is a new, never-modified version file; the newest `versions_to_keep` + the first of each day
  are kept. Deleting moves to the recycle bin (trash); restore brings back the item and its versions.
  Trash is not purged automatically (a later admin setting: purge after N days, super-admin only).
- Pulled, append-only backups on dspeter (old versions survive even if the server is wiped).
- The sync client (D2) never propagates a mass delete or mass rewrite without asking (threshold), and
  always uploads as new versions.
- **Audit log** (D1): append-only table of security-relevant events (sign-in ok/failed, password
  change/reset, account/org/membership/role changes, share/unshare, link create/delete, delete/restore/
  purge, admin actions) with who, when, IP, item/org. Viewable in /admin (super-admin: all; org admin: their
  org). Never contains passwords, tokens or file contents. **(exists, see below)**

### Server contract for the Drive web app (D1, `drive-server` branch) **(exists)**

The Drive page is served by freedomoffice-server from the same origin as the API (`public_url`), so it
calls `/api/*` with `fetch(..., { credentials: "same-origin" })`. The server sends no CORS headers: other
origins can't read anything. Code: `server/src/web.rs` (session), `server/src/content.rs` (bytes),
`api::audit_as` (audit).

#### Web session (cookie + CSRF header)

| Endpoint | Request | Answer |
|---|---|---|
| `POST /api/web/login` | `Content-Type: application/json` (required; 400 otherwise), body `{username, password}`; `Origin` (or `Referer`) must be the server's own and `Sec-Fetch-Site`, if sent, `same-origin`/`none` (else 403 `cross_site`) | 200 `{user, csrf}` + `Set-Cookie`; 401 wrong username or password, or a disabled account (the same answer); 429 limited |
| `GET /api/web/session` | the cookie | 200 `{user, csrf}`, or 401 `{"error"}` without a valid session (also while a temporary password is set: then `user.must_change_password` is true) |
| `POST /api/web/logout` | the cookie + `X-FO-CSRF` | 204 and the cookie cleared (also with no session) |

- `user` is the same object as in `/api/login`: `{id, username, display_name, email, is_admin, root,
  must_change_password}`. `GET /api/me` adds `orgs`.
- Sign-in runs `api::check_sign_in`, the same path as `/api/login` and `/admin/login`: invalid usernames
  refused first, the attempt counted up front in the shared limiter (per address and per username: the
  three sign-ins share their counts), the delay after repeated failures, Argon2 in its semaphore. A browser
  that signs in again ends the web session of the cookie it sent.
- Cookie: `__Host-fo_web=<secret>; Path=/; Max-Age=43200; HttpOnly; SameSite=Strict; Secure` (32 random
  bytes, base64url). On a plain-http loopback setup (as for `/admin`): `fo_web=...` without `Secure`.
  Stored as `admin_sessions` rows with `kind = 'web'` (only the SHA-256). 12 h absolute, whatever the
  activity; at most 10 web sessions per person (the oldest end; admin sessions are counted separately). A
  web session never opens `/admin`; an admin session (`__Host-fo_admin`) never opens the API.
- `csrf` = base64url(SHA-256("freedomoffice web csrf\0" + secret)): one per session (stable for its life),
  nothing stored, unknowable without the HttpOnly cookie. Keep it in memory (re-read it with
  `GET /api/web/session` after a reload).
- **Every `/api/*` endpoint** accepts the cookie instead of `Authorization: Bearer`. A request that has an
  `Authorization` header is judged by that header alone, exactly as before (cookie ignored).
  With the cookie:
  - every method except GET and HEAD must send `X-FO-CSRF: <csrf>` (constant-time compare; missing or wrong
    → 403 `{"error", "code": "csrf_failed"}`) and come from the server's origin (`Origin`, or without one
    `Referer`, must be `public_url`'s origin; `Origin: null` is refused) → else 403 `code: "cross_site"`;
  - any method with `Sec-Fetch-Site` other than `same-origin` or `none` (`same-site` = a sibling
    subdomain, `cross-site`) → 403 `code: "cross_site"`;
  - the live WebSocket (`GET /api/items/{id}/live`) never takes the cookie: get a ticket with
    `POST /api/items/{id}/live-ticket` (cookie + `X-FO-CSRF`) and connect with `?ticket=` (single use,
    60 s; the ticket remembers the web session and is re-checked like any live connection);
  - a temporary password gates the cookie like a token: 403 `password_change_required` everywhere except
    `/api/me`, `/api/me/password {old_password, new_password}` (cookie + `X-FO-CSRF`), `/api/logout`,
    `/api/web/session`, `/api/web/logout`.
- Web sessions end with `/api/web/logout`, `/api/logout` (with the cookie; it then also clears the
  cookie with `Set-Cookie`), "sign out of all devices"
  (`POST /api/users/{u}/sign-out`, admin page), disabling the account, a password reset, any password change
  (from a device or the admin page: all of them; from the web: all others), and an administrator ending one
  (`DELETE /api/users/{u}/sessions/web/{id}`; `GET .../sessions` lists them under `web` with
  `kind: "web"`, next to `kind: "admin"`). The Drive app should treat any 401 as "signed out" (show the
  sign-in) and any 403 `csrf_failed` as "reload the session" (`GET /api/web/session`).
- Errors keep `{"error": "<for people>"}`, sometimes with `"code"`: `csrf_failed`, `cross_site`,
  `password_change_required`, `wrong_password`, `links_disabled`, `invite_required`. 401 = not signed in,
  404 = doesn't exist or not visible, 403 = visible but not allowed (view-only, not a manager), 409 name
  taken / conflict, 408 an upload stalled, 412 `If-Match` mismatch, 413 too large, 416 bad range, 423
  being edited live, 429 limited (sign-in attempts, or more than 4 uploads at once), 507 the server's disk
  is nearly full.
- Every request's store work is one SQLite transaction (`BEGIN IMMEDIATE`, so a CLI writing at the same
  time makes it wait rather than fail half-way; nested work uses savepoints): a change and its audit row
  are kept together or not at all, so an error answer never follows a change that was made. Files follow
  the transaction: version files a save prunes are deleted only after the outermost commit (a nested
  rollback forgets them), and files written by work that rolls back (or panics) are removed again.

#### Downloads (`GET /api/items/{id}/content`, `/l/{token}/download`)

- Query: `version=<n>` (an older version; not for share links), `download=1` (save rather than show).
- Streamed from disk (never read whole into memory). `Accept-Ranges: bytes`; one range per request
  (`bytes=a-b`, `bytes=a-`, `bytes=-n`) → 206 with `Content-Range: bytes a-b/len`; outside the file → 416
  with `Content-Range: bytes */len`; several ranges or a malformed header → 200 with all of it; `If-Range`
  with another ETag → 200 with all of it.
- `Content-Type` from the extension, from a fixed list (txt/log/md, csv, json, pdf, png, jpg/jpeg, gif,
  webp, svg, html/htm, xml, mp3, m4a, wav, ogg/oga, mp4/m4v, webm, mov, zip, xlsx, docx, pptx, xls, doc, ppt,
  ods, odt, odp); anything else `application/octet-stream`.
- `Content-Disposition: inline` (or `attachment` with `download=1`, and always for `/l/` downloads)
  `; filename="<ASCII fallback, other characters as _>"; filename*=UTF-8''<percent-encoded name>`.
- Always: `X-Content-Type-Options: nosniff`, `Cross-Origin-Resource-Policy: same-origin` (other sites
  can't embed the bytes with the visitor's cookie), `Referrer-Policy: no-referrer`, `Cache-Control:
  no-store`, `ETag: "v<version>-<hash12>"`, `X-Version`. `Content-Security-Policy: sandbox; default-src
  'none'; img-src data:; style-src 'unsafe-inline'; media-src 'self'; frame-ancestors 'self'` for every type
  except PDF (`frame-ancestors 'self'` only; PDF viewers refuse to run sandboxed): a shared HTML or SVG
  file renders without script in an opaque origin, never as the server's origin. The Drive page may show
  previews in an `<iframe>` of its own origin.
- **Trust boundary (accepted for now):** HTML, SVG and XML that people upload are served from the
  server's own (trusted) origin, protected only by the sandbox CSP, nosniff and CORP. PDF gets no sandbox
  (Chrome and Firefox refuse to show a PDF in a sandboxed document; their viewers run PDF scripts
  isolated from the page). A browser that ignored CSP `sandbox` would run uploaded HTML as the server's
  origin. **Long term:** serve user content from a separate origin (e.g. `usercontent.<domain>`, with
  signed short-lived URLs and no cookies), as Google Drive and GitHub do.
- `/api/items/{id}/content` (current version) also keeps Sheets' live headers (`X-Live-Seq`,
  `X-Live-Sheets`, `X-Live-State`).

#### Uploads

- `POST /api/files?parent=<folder id or empty for My files>&name=<name>&conflict=fail|rename|replace` with
  the raw bytes as the body (no multipart; one file per request; send `Content-Length`, chunked works too).
  201 + item for a new file, 200 + item for a new version (`replace`), 409 name taken (`fail`, checked
  before the body is read), 423 replacing a workbook that is being edited live.
- `PUT /api/items/{id}/content` (optional `If-Match: "<etag>"`) → 200 + item (`ETag` header): the next
  version; 412 `{error, etag, version, modified_by, modified}` when someone saved meanwhile; 423 live.
- Both: authorization (and `If-Match`, the name, the conflict rule) are checked before the body is read and
  again before it is stored; the body streams to `<data_dir>/incoming/` (hashed on the way) and is moved
  into `files/<id>/<version>` with one rename; past `max_upload_mb` the upload stops at once with 413
  `{"error": "The file is too large (at most N MB)."}` (also when Content-Length says so up front); an
  interrupted upload stores nothing; `incoming/` is emptied at start. Progress: use `XMLHttpRequest`
  `upload.onprogress` (fetch has no upload progress).
- Limits: at most 4 uploads streaming at once per person (or share link) → 429 `{"error"}` for the fifth
  (the Drive app should queue: upload 4 at a time); an upload that sends nothing for 60 s is stopped →
  408 and nothing is kept; before staging, the data disk must have `max_upload_mb` + 1 GB free → else 507.
- `POST /api/items/{id}/versions/{n}/restore` copies the old version on disk (no memory buffering).
  **M4:** restoring is allowed while people are connected (423 stays only when nobody is connected but
  committed live changes aren't in a version yet): every open session of the file is retired, each
  connection gets `reload` and closes, a late batch of the old session is answered with `reload` and
  stored nowhere, and the restored file starts a new live base (clients keep their unsent changes and
  rebase them on the restored file). Changes committed since the last snapshot are not in any version
  and are not recoverable after a restore while connected (known limit; the last snapshot is at most
  15 s to 2 min old).
- `GET /api/items/{id}/versions` entries gained (additive) `label` ("" = none) and `contributors`
  (display names of the users whose live batches are in a live snapshot, in order of first change; `[]` for
  uploads, saves and restores, which only have `modified_by`). `PUT /api/items/{id}/versions/{n}` with
  `{"label": "..."}` (editors; 404 unknown version, 400 without `label`) names a version (trimmed, control
  characters dropped, 80 characters; empty clears). Named versions are never pruned; they don't count
  towards `versions_to_keep`. Stored in `version_meta` (schema 5; an older server refuses a v5 database).

#### Audit log

`audit(id, at, actor_id, actor_name, ip, action, org_id, item_id, target_user, detail)`, append-only (SQLite
triggers abort updates and deletions of rows younger than 365 days); pruned after 365 days at server start
and daily. `actor_name`/`target_user` are usernames at the time; `ip` the client address (behind the trusted
proxy, `X-Forwarded-For`); `org_id` is the organisation the event belongs to (for item events: the item's
organisation, so org admins see what happens in their org folder); `detail` is one line of at most 200
characters. **Never** passwords, tokens, invite or link secrets, or file contents (file and folder names
and the email an invite was made for are recorded). A username that was typed at a failed sign-in is
recorded only if that account exists (people type passwords into the username field).

**Counting repeats.** Some events are counted instead of stored one by one: a repeat with the same key
within 60 s of the row's first event adds 1 to its `count` (and sets `last_at` and `last_detail`, the
latest repeat's detail); the row keeps the first event's details. Keys: `sign_in.failed` per network
(IPv4 address, IPv6 /64) and account (all unknown usernames from one network share one key);
`item.rename`, `item.move` and `file.version` per actor and item; `folder.create` per actor and parent
folder (`item` is the first folder). /admin/audit shows "xN until <time>" and the last detail. So a rename loop or a password-guessing run adds about one row a minute, not one per request.

**Erasing.** `freedomoffice-server --config <cfg> audit-prune --before YYYY-MM-DD [--user USERNAME]` (CLI,
stop the server first) deletes the events before that date (UTC), or only those done by or to that person.
In one transaction it drops the early-deletion trigger, deletes, recreates the trigger and records an
`audit.erase` event (count and date, never the person's name). This is also how a request to erase
someone's personal data from the log is honoured.

jump over data. Tapping a column/row header selects it and opens its menu (Cut/Copy/Paste, Insert 1..n left/right or
above/below, Delete, Hide, Unhide next to hidden ones, width/height with a - / + stepper and live preview, Clear,
Freeze up to here); a size handle on the selected header drags the width/height, its end handle extends the run;
the corner tap selects all. The tool row (scrolls sideways, 44 px targets) has bold, italic, underline, strike, text
and fill colour palettes (48 swatches plus `#rrggbb`), alignment (horizontal buttons, a sheet for vertical/indent),
wrap, borders presets, number formats (General, Number, Thousands, Whole, Currency, Percent, Dates, Time, Scientific,
Text), text size, merge/unmerge, freeze panes (top row, first column, at selection, off) and Clear contents/formats/
all. Desktop: Ctrl/Cmd+C X V (system clipboard as TSV, paste also from other programs), A, D, R, B, I, U, F (find),
G (go to), Z/Y, Delete; a fill handle at the selection's corner (a pointer device only). Tabs: tap to switch, `+`
to add, long-press for a menu (Rename, Move left/right, Tab colour, Hide, Show a hidden sheet, Add, Delete with a
confirmation), or long-press and drag to reorder. Search (magnifier or Ctrl/Cmd+F): live results, "n of m",
next/previous, options (case, whole cell, formulas, workbook/sheet); tapping the address box (Ctrl+G) goes to
`B7`, `A1:C5`, `Sheet2!C3`, `B:D` or `3:5`.

**Phones.** If the connection drops, edits made meanwhile (cell entries, format, structure) wait in an in-memory
queue (not persisted; at most 300 changes / 2 MB; typed text stays visible), the status says "Offline - n
waiting", and after the automatic reconnect they are re-sent in order and a toast says "Reconnected. n changes
re-sent." Queued changes name their sheet by id so a reordered sheet list doesn't misdirect them; the undo history
belongs to the connection and starts empty after a reconnect. Every refusal (view-only, limits, unreadable formula,
duplicate sheet name...) shows as a toast. The page follows the visual viewport (on-screen keyboard) so the
formula bar stays visible, uses safe-area insets, 16 px inputs, and menus open as bottom sheets. The grid ignores
long-press callouts and text selection; pinch still zooms.

**CLI / MCP parity.** The headless client already covers Sheets for agents: `fsheets` (CLI) and its MCP server read
and edit through the live protocol (agents/README.md). The viewer's JSON is also usable by scripts
(`curl` with a bearer token against the routes above), which gives agents a rendered-values read without the
live engine; no new CLI or MCP verb is needed for W1.

### Open in FreedomSheets

Drive links to `freedomoffice://open?server=<percent-encoded public_url>&item=<id>` for `.xlsx`, `.xlsm`, `.csv`,
`.fsheet`. FreedomSheets registers the scheme (Windows: `HKCU\Software\Classes\freedomoffice`, written at
start only if missing, already pointing at that exe, or pointing at an absolute exe path that no longer
exists; Linux: `MimeType=x-scheme-handler/freedomoffice;` in
its .desktop file, see README; macOS: `CFBundleURLTypes` in the app bundle). Sheets accepts only exactly
`server` (https, or http on 127.0.0.1/localhost) and `item` (32 lowercase hex) and uses nothing else from
the URL. With one signed-in account for that server it opens the item (joining live when possible); with
two or more it asks which account. For a server with no signed-in account it first asks "This link points
to <host>, a server you haven't signed in to. Only continue if you trust it." (the host decoded from
punycode, with the `xn--` form next to it, or the raw host plus a look-alike warning when it can't be
decoded); only Continue leads to File > Account with the server filled in, and only then does the file open
after that sign-in. It never signs in or sends credentials by itself.
